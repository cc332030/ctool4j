
# 测试规范

以下规范适用于本项目所有模块的单元测试（JUnit 5）与性能测试（benchmark）。

## 单元测试

### 目录结构与命名

- 测试类与源类包路径保持相同：测试类（`src/test/java`）的包路径与对应源类（`src/main/java`）一致（如源类 `com.c332030.ctool4j.core.util.CEntityUtils`，其测试类 `CEntityUtilsTests` 应位于同包 `com.c332030.ctool4j.core.util`），不额外加 `test` 段等路径层

### 用例设计

- 测试目标：优先覆盖"容易出错或出错后难发现"的方法，含正常路径、边界与异常路径；异常断言用 `assertThrowsExactly` 精确匹配异常类型，不用 `assertThrows`（避免父类异常掩盖子类语义）
- 用例设计流程：测试用例生成须依照白盒原则与黑盒原则分别生成，再以错误推测法、状态迁移测试、行为一致性检查补充，最终合并去重——
  - 白盒原则（基于实现分析）：先理清被测方法"做什么用的、有哪些场景"，再分析方法的具体实现：分析代码可能存在的问题、支持的参数形态；对正确的参数和错误的参数分别添加测试用例，正例、反例、边界值都要覆盖；异常输入按实际使用场景决定（见下条）；复合条件分支（如 `if (a && b)`）按判定/条件覆盖分析，覆盖各条件组合，避免短路掩盖分支；循环与递归按路径覆盖分析——循环体覆盖 0 次、1 次、多次及边界次数，递归覆盖深度边界
  - 黑盒原则（基于功能规格）：根据方法的功能添加正常和异常的用例；根据入参、出参分别分析入参与出参的取值范围，无论有效还是无效，都取代表性值添加测试用例（如典型值、边界值、越界值、非法值等）；检查入参、出参取值是否能覆盖所有情况，取值过多（无法穷举）时抽样，抽样须覆盖各取值区间与类别（如典型、边界、非法等）的代表值；多个入参条件组合决定行为时用决策表分析组合，条件多、组合爆炸时用配对抽样（如 pairwise）结合代表性值缩减组合量；检查方法有没有意料之外的输出
  - 错误推测法（经验补充）：结合经验补充白盒、黑盒之外的易错场景——空/空集合、重复调用与幂等性、转义字符、Unicode 边界（如 `Character.MAX_VALUE`）、时区/夏令时、数值溢出（如 `Integer.MAX_VALUE + 1`）、浮点精度等
  - 状态迁移测试：有状态对象/服务（如缓存、redis 服务等）按状态迁移设计用例，覆盖合法迁移路径与非法迁移（不允许的状态转换）路径
  - 行为一致性：异常发生后对象内部状态/不变量不被破坏、资源正常释放（见 AGENTS.md 修复约束）；多线程并发调用（缓存、单例、lazy 初始化等共享场景）下结果一致
  - 合并去重：白盒、黑盒及补充方法生成的用例最终合并去重，形成最终用例集；场景未测全不视为完成；场景拆解注意按输入形态变体穷举（如分隔符/标志片段的有无、有无值、多片段、片段值内再含分隔符等），避免只覆盖典型形态漏掉变体
  - 记录：白盒原则、黑盒原则及补充方法（错误推测法、状态迁移测试、行为一致性）的分析过程，与合并后的用例结果，须记录到测试设计文档（大范围或复杂测试）或测试代码注释，不留存于临时产物（临时产物统一写入 `tmp/` 文件夹，见 AGENTS.md"临时产物统一目录"条目）
- 分支输出覆盖：被测方法存在分支（if/switch/多态分发等）时，设计用例须覆盖每种分支情况，且每种分支都须有测试用例验证其输出（结果/格式）满足要求——不得只覆盖部分分支、或仅验证分支被触达而不验证分支输出；分支多、组合爆炸时聚焦有语义意义的分支，配合全组合（全字段）用例兜底整体格式
- 异常输入用例按实际情况取舍：若方法虽未注明非空、但实际使用中保证不会传空值（如内部自用、调用方契约已保证），可跳过该参数的异常输入用例，但必须在参数上标注非空注解（如 `@NonNull`）写明约定，防止后续误判为可空、再次生成异常输入用例；真实场景可能传入空值或非法值时，异常输入用例必须覆盖，且异常输入用例的测试数据不限定范围与内容——应覆盖任意异常输入（如笔误值、随意捏造值、不在枚举/关键字集合等范围内的值），不得只测少数几个看似合理的非法值
- 最真实场景优先：测试用例尽可能满足最真实的场景——测试数据、调用方式、输入/输出形态要贴近真实使用场景，不得用过于理想化或脱离实际的数据；能用完整真实流程（如走 JSON 反序列化、经 Spring 容器校验/注入、经真实组件栈）就不绕过它简化（如直接字段赋值、脱离容器直接 new validator）；验证端到端行为（如接口入参校验、文档生成）时用真实入口（如 MockMvc 调接口、访问真实端点），而非只测内部单点；在贴近真实场景的基础上仍须保留边界与异常用例（见白盒/黑盒原则），不得因"贴近真实"而牺牲用例完整性
- 不得为测试新增专用方法/分支：测试应在被测功能真实的流程与节点上选取节点按正常流程进行（如有多个处理节点，按真实流程组合其中节点测试，覆盖正常路径与各分支），不得在真实流程之外再开发新方法、新分支节点仅为测试所用——存在仅被测试调用的方法/分支说明功能设计上有多余节点，应删除该节点并将测试改到真实流程上（如为拼接字符串的方法做测试，应测真实调用该方法的上层完整流程，而非单独测这个无真实调用的拼接方法）

### 用例编写

- 测试代码也需严格遵守全部项目规范：测试代码与主代码同等遵守 AGENTS.md 及各规范文件（AGENTS-JAVA.MD、AGENTS-CODING.MD、AGENTS-SYNTAX.MD、AGENTS-SPRING.MD、AGENTS-MAVEN.MD 等），不得因是测试代码而放宽——如 lombok 使用、构造器/字段修饰符、对象创建用 builder、命名与注释、语法糖等一律按主代码标准执行；语言层面保持 Java 8 目标，禁用 `List.of`/`Map.of` 等新语法糖（见 AGENTS-JAVA.MD、AGENTS-SYNTAX.MD）
- 测试以正确规格为准，不迁就源代码：用例与源码冲突时，用例按正确规格书写，必要时修复源代码，不得用错误的用例迁就源码；测试不通过不代表该场景不用测，不通过更要测（先按正确用例暴露问题，再修复源码直至通过）
- 涉及 lombok 等语法糖时注意实际展开结果（如 `val` 的类型推断），避免用例预期与实际不符
- 含 null 元素的集合字面量需显式泛型（如 `Arrays.<Integer>asList`），避免类型推断歧义
- 依赖反射/序列化（Jackson、hutool 等）的测试注意资源释放（如 generator 需 close）与构造器可见性（反射默认只取 public 构造器）

### 执行与验证

- 验证以 Maven 结果为准：Windows cmd 下编译失败 exit code 可能为 0，不得仅凭 exit code 判断，必须依据 surefire 的 Tests run/Failures/Errors/Skipped 统计判断是否通过；输出优先重定向到文件（如 `mvn ... > build.log 2>&1`，避免终端/IDE 输出截断丢失统计，见 AGENTS.md 编译验证条目），获取统计须一步直接到位——从重定向的日志文件中用 findstr/grep 过滤统计行（同一命令内串联完成），一次拿到结果，禁止两段式"先运行、再提示后单独读取报告"的流程，也不得反复附提示性说明
- 同一 Maven 模块禁止并行构建；多 agent 协作时同一模块分阶段执行（先写测试文件，再串行执行验证），避免构建冲突
- 测试失败判定：当测试用例失败且确认不是本次改动造成（多为人工改了代码但未同步调整测试用例时）时，以代码为准——测试用例过时，应更新测试用例使其与当前代码行为一致，不反过来改代码迁就测试

### 环境与兼容

- 外部服务替代：依赖 redis、db 等外部服务的类、方法，若存在测试专用或嵌入式的同类实现（如嵌入式 Redis、H2/内存数据库），运行测试时优先用它替代验证，不得因本地无对应环境而跳过测试或删减用例
- 兼容性测试：覆盖易受环境影响输入的稳定性验证（如时间/日期格式、字符集、不同环境或依赖版本的差异等），验证行为在不同条件下表现一致；兼容性验证分两类——
  - 功能完整性测试（必须）：重构/优化前后行为一致性验证（如内嵌旧语义参考实现逐字段对比），确保优化不改变既有行为；属功能完整性范畴，是每次重构/优化的必备项
  - 源代码兼容性测试（尽力而为）：源码与编译产物的跨环境兼容，不因小优化牺牲兼容性（Java 跨平台）。场景包括：JDK 版本升级后可用性（含编译级别与运行环境不一致——如 jdk8 编译、jdk7 运行的 class 文件与 jdk7 编译的不一致，继承 ConcurrentHashMap 等存在 JDK 内部实现变更的类时会运行报错）、跨操作系统（Windows 与 Linux 等差异）、开发环境特殊依赖（如开发时使用的特殊环境变量在真实运行时可能不存在）；能测则测，无法执行的场景须记录用例设计、考量与限制，不得因环境受限而删减记录

### 测试文档

- 测试代码比工作代码更重要——测试是行为规格的载体，须认真维护并同等对待；测试行为设计（测试架构与组织、测试手法与参考实现、为什么这样测、测试边界与取舍）统一写入设计文档的"测试设计"章节（与功能设计放同一文档，见 AGENTS.md"设计文档"条目），避免测试设计文档分散；用例级细节（测试数据、具体断言技巧、已知限制与未覆盖场景、兼容性考量能测的与不能测的）写在测试代码注释或对应文档，与 javadoc 用途不同（javadoc 面向 API 使用方说明语义，测试注释面向测试维护者）；大范围或复杂测试（如兼容性测试、重构验证测试）须在用例设计时同步编写设计文档"测试设计"章节
- 测试用例文档（测试方法不要求 javadoc，以本条为准）：测试用例须维护完整的测试文档，统一放在 `doc` 目录下（禁止放 `tmp/` 目录），文件名与所测功能/类对应；文档中测试用例须**分类 + 编号**（如 1 请求日志拼接、1.2 响应报文头、1.2.5 响应头多值输出），分类与编号须有层级、按功能/行为维度组织，便于从文档了解测试范围、检查是否有遗漏；**测试类须在类上声明是哪个功能哪个类的测试用例**（如"`CCommUtils`（web 工具类）请求日志拼接的测试用例"），**测试方法须标识其对应的分类与编号**（如"对应测试用例 1.2.5"），使代码与测试文档可互相定位；新增/调整测试用例时须同步更新测试文档（增删改对应分类下的编号），保证文档与代码一致；测试方法不必写 javadoc，场景/边界/考量通过测试文档 + 测试类/方法上的编号标识覆盖；测试用例文档还需写明**用例设计的思路与依据**——设计该组用例的思路（按什么维度组织、为什么选这些场景/边界/反例、覆盖哪些行为与易错点）、依据（需求/规范/设计文档中的依据，或等价类/边界值/分支覆盖等测试方法的依据），使从文档能理解"为什么这样设计测试"，便于评估用例设计是否合理、是否有遗漏

## 性能测试

- 独立性：性能测试独立于单元测试（不随 mvn test 执行），打包时不执行，仅在明确命令执行性能测试时才执行
- 对比测试：性能测试须为对比测试，对比常用的同类实现方式与工具，实现方式类别至少 3 类（不足 3 类时按实际可用数量对比）
- 排除初始化干扰：性能测试需测试两次，第二次须在全部实现方式均初始化完成后再进行（首次结果含初始化/加载开销，不计入最终结论）
- 结果分析：测试完成后须分析性能差异由哪些原因引起（如实现原理、初始化/缓存开销、反射/序列化开销等），并给出对应的解决方案
