
# 文档规范

以下规范适用于文档、注释、设计文档的编写。

## 注释与文档

- 注释与文档：不写死常量数值，用抽象描述或引用常量名；代码注释仅记录局部决策与要点（如初次设计、反复修改、有争议时的方案依据与设计思路：为什么这样做、为什么不做其他方案、接受了什么边界），不追求完整设计叙述——完整设计（功能怎么设计、用例考虑、兜底、适用范围等）统一写入设计文档（见"设计文档"条目），避免注释东一块西一块不完整；常规小改动不强制备注；总纲：一切有价值的内容都需记录——设计决策、方案取舍、约束边界、兼容性考量、测试设计、问题处理等，按内容性质写入合适的持久位置（设计文档、代码注释/javadoc、README、规范文件等），不遗漏、不依赖记忆，临时产物除外（见 AGENTS.md「临时产物」条目）

## 设计文档

- 设计文档：核心功能的新增、重构（含行为变更、方案选型、有取舍的设计）必须编写或更新设计文档，记录当时考虑到的所有东西：功能设计（方案是什么、为什么这样做、备选方案及不选原因）、测试设计（测试行为本身的设计：测试架构与组织、测试手法与参考实现、覆盖哪些场景、为什么这样测、测试边界与取舍）、兜底（有哪些兜底、兜底触发条件与边界）、适用范围（适用场景、不适用场景、已知限制与取舍）；功能设计与测试设计放在同一设计文档内（测试是功能的验证规格，二者一体，避免文档分散）；文档按模块建立子目录存放：根目录 `doc/design/<模块>/`（如 `doc/design/core/CBeanUtils.adoc`，模块名取核心功能/组件所属模块，如 core/web/feign/log），功能与测试文档成对放在同一模块子目录下（`Xxx.adoc` 设计、`XxxTests.adoc` 测试）；AsciiDoc 格式；文档随代码演进同步更新，新增、重构时必须处理
- 代码与文档互相引用：代码与设计文档必须**双向可定位**——文档须写明所对应功能的模块与全限定类名/方法（从文档能找到代码），代码（类/方法的 javadoc 或注释）也须显式引用对应的设计文档相对路径（从代码能找到文档），二者任一处都能顺利跳转到另一处；代码侧统一在该类/方法的 javadoc 用 `@see doc/design/<模块>/<Xxx>.adoc` 指向设计文档（如有对应测试文档一并 `@see`），类级 javadoc 指向 `Xxx.adoc`、方法级 javadoc 指向其所属功能文档（多方法同文档时类级已引用即可，方法级按需补充定位锚点）；新增/重构代码时同步补齐双向引用，缺失引用的旧代码发现后直接补，不遗漏
- 设计文档须记录已知缺陷与不足：设计文档除记录设计本身，还须**显式记录当前工具类、方法、字段的已知缺陷、不足与注意事项**——包括但不限于：
    - 易误用点：调用方可能踩坑的入参/出参假设、线程安全、可变状态被共享修改等
    - 边界与异常：异常未处理/吞掉、空值/超长/超大输入等
    - 默认值：字段/参数的默认值及其语义（如"0 表示未测量 / null 表示未采集"等易混淆约定），默认值可能引发的行为差异与误判
    - 可能引发的问题：如拼接日志时异常静默导致主流程中断、字段不同步、序列化兼容等
    - 性能瓶颈：大对象/循环内分配、正则/反射/序列化开销、阻塞 IO、O(n) 隐患等
    - 可能影响的功能：当前缺陷/不足/默认值变更会波及的其它功能、调用方或下游逻辑（如某字段默认 0 会影响耗时统计、日志格式、监控告警等），须列出受影响范围以便评估改动
    ；记录粒度到"工具类→方法/字段"层级，按类/方法/字段分段标注，能定位到具体代码；缺陷内容随代码演进同步更新（修复后标注已解决或删除），不遗漏、不依赖记忆

## 文件格式与编码

- 文件格式与编码：除 AGENTS.md 外，其他文档优先使用 AsciiDoc（.adoc）格式；所有文件一律 UTF-8 编码，除非明确不是 UTF-8（如特定二进制格式、明确指定其他编码的文件）
- 文档代码块：md/adoc 文档中代码块的语言标识须与实际内容匹配——代码块虽不要求编译通过，但必须满足所标识语言的基本语法（避免 IDE 语法检查报红）；无法保证语法正确时标识为无格式类型（如 `text`），优先使用带格式的准确语言标识（如 `java`、`xml`、`bash`）；伪代码/结构描述等非语法内容不得标注具体语言
- 文档问题：javadoc、注释、README 等纯文档性缺陷，发现后直接修复，无需问询
