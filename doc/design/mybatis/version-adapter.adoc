= MyBatis-Plus 版本适配层（base 内差异层 / 版本模块） 设计文档

模块：ctool4j-mybatis-pom（`ctool4j-mybatis-base`——内含 `spi` 差异层档位源目录、`ctool4j-mybatis-33`、`ctool4j-mybatis-34`、`ctool4j-mybatis`）
状态：已落地（差异层曾独立为 adapter 模块、后并回 base 的档位源目录；两档位构建通过）
适用范围：同一套业务 service / controller 代码在 mybatis-plus 3.3.x / 3.4.x / 3.5.16 / 3.5.17 上编译与运行

== 背景

本库的 service 契约（`ICService` 一族）与实现基底（`CServiceImpl`）要被**四个 mybatis-plus 版本**的引用方共用。四个版本的真实差异经字节码实测如下（坐标与类结构均取自 Maven Central 的正式构件）：

[cols="2,2,2,2", options="header"]
|===
| 项目 | 3.3.2 / 3.4.3.4 | 3.5.16 | 3.5.17

| `IService` / `ServiceImpl` 包名
| `com.baomidou.mybatisplus.extension.service`
| 同左（构件已拆到 `mybatis-plus-spring`，**包名未变**）
| `com.baomidou.mybatisplus.spring.service`

| `ServiceImpl` 的 `entityClass` 字段
| `protected`（3.3 为 `Class<?>`，3.4 为 `Class<T>`）
| `private`（`AbstractRepository`）
| `private`（`AbstractRepository`）

| `getEntityClass()`
| 3.3 **无**；3.4 有
| 有
| 有

| `currentModelClass()`
| 3.3 / 3.4 有
| 无
| 无
|===

结论：**只有"包名"这一条是两侧都要处理的差异**；`getEntityClass` 的缺失只发生在 3.3，且无法用"读字段"绕过（3.5.16 起字段是 `private`，见下「为什么 `getEntityClass()` 放在 base 的 `CServiceImpl`」）。

== 方案：base 内分差异层 + 版本模块

[cols="1,2,2", options="header"]
|===
| 层 | 模块 | 职责

| 差异层
| `ctool4j-mybatis-base` 的 `spi` 档位源目录（`java-jdk8` / `java-latest`，原 `ctool4j-mybatis-adapter`，已并回）
| **唯一**知道 MP 包名的地方：以中性全限定名承接 `IService` / `ServiceImpl`，并吸收空安全语义。**也是本族唯一允许多源目录的落点**

| 公共层
| `ctool4j-mybatis-base` 的公共源目录（`src/main/java`）
| 版本无关的契约与实现基底：`ICService` 一族、`CServiceImpl`、mapper / model / handler / controller。**单源**

| 版本模块
| `-33` / `-34` / `ctool4j-mybatis`
| 版本专属装配（配置、SQL 注入器、枚举接口）。**单源，只吃 base 的 jar**
|===

=== 多源只有一种形态：档位源目录追加其一

本层的版本适配用*追加*形态（与容器适配同形，但差异类型不同——这里是 MP 包名、那里是 `javax`/`jakarta`）：

* base：`src/main/java`（公共契约与实现）+ 档位源目录 `src/main/java-latest`（3.5.17+ 侧）与 `src/main/java-jdk8`（< 3.5.17 侧）——两个档位目录同名同包、按档位只追加其一，追加语义天然互斥；档位目录里只有那三个按版本侧各写一份的类，没有公共源码；
* `-33`、`-34`、`ctool4j-mybatis`：单源目录 `src/main/java`，**不得**再用 `srcDir` 挂别的模块的源码目录，也不得再有第二个源目录。

`java-jdk8` / `java-latest` 由根脚本按 `JDK_VERSION` 自动追加其一，无需任何模块级开关。

=== 差异层的两个档位目录（互斥，只处理包名）

[cols="2,1,1,2", options="header"]
|===
| 目录 | 承接的 MP 坐标 | 生效档位 | 谁用

| `src/main/java-latest`
| `com.baomidou.mybatisplus.spring.service`
| 最新 LTS
| base 自身；`ctool4j-mybatis` 经 jar 拿到

| `src/main/java-jdk8`
| `com.baomidou.mybatisplus.extension.service`
| jdk8
| base 自身；`-33` / `-34` / `ctool4j-mybatis` 经 jar 拿到
|===

两侧各三个文件、**同名同包**（`com.c332030.ctool4j.mybatisplus.spi` 下）：`IService`、`CMybatisPlusSpi`、`CMybatisPlusServiceImpl`。jar 里因此只有一侧的 class。

**追加即互斥**：两个档位目录永不编进同一档——同一次编译只追加其一，不存在"同包同名重复"的可能；
根脚本的 `assertNoDuplicateJavaSources` 只查「同一档纳入的多个目录」，档位目录与公共源目录之间不相交，天然通过。

=== 关键机制：中性全限定名

三个类的**全限定名在两侧完全相同**，被绑定的 MP 坐标藏在类体内（`extends com.baomidou...` 那一行）。于是：

* `ICService.class`、`CServiceImpl.class` 里**不出现任何 MP 包名**，一份 jar 可被两侧共用——"多份 `CMybatisPlusServiceImpl`、同一时刻只有一份生效"指的就是这件事；
* 其余模块**只依赖 base 的 jar**，不再用源码覆盖它。jar 的档位侧与档位内的 MP 版本同侧：jdk8 档的 `-33` / `-34` 拿到的 extension 侧 class，其唯一的上游引用是 `extension.service.IService` / `ServiceImpl`——这两个坐标在 3.3 / 3.4 / 3.5.16 里都存在且方法描述符一致（见「跨版本二进制契约」），故**按 3.5.16 编出的这份 class 在 3.3 / 3.4 上同样可链接**。

代价与边界：latest 档的 jar 是 spring 侧，与 3.3 / 3.4 不可能共存——因此 `-33` / `-34` **只在 jdk8 档位构建与发布**（见「已知限制」第 5 条）。

`CServiceImpl` 里没有任何版本分支：`getEntityClass()` 由它自己沿泛型解析（四个版本都成立），
元素级方法的三处消歧（`getById` / `getOptById` / `listByIds`）由它转交 `ICService` 的空安全 default。
两侧的适配桥（`CMybatisPlusSpi` / `CMybatisPlusServiceImpl`）因此保持零业务逻辑。

=== 为什么 `getEntityClass()` 放在 base 的 `CServiceImpl`

`ICBizIdService.getEntityClass()` 是抽象契约，3.3 的上游没有实现，必须自己补。可想的三种取法没有一个跨四个版本成立：

* 读 `entityClass` 字段：3.3 / 3.4 可读，**3.5.16 起是 `private`**（且已挪进 `AbstractRepository`），不可用；
* `currentModelClass()`：3.3 / 3.4 有，3.5.16 起已删除，不可用；
* `getEntityClass()`：3.3 没有，只能自己给。

三条路都不跨版本，故改用**纯泛型解析**（不碰 MP 内部字段，四个版本行为一致，语义与 MP 自身实现相同）：沿 `getClass()` 的父类链找第一个「实参为具体类型」的参数化父类，取第 2 个实参（`CServiceImpl<M, T>` 的 `T`）。

放在 base 公共源而不是差异层，是因为它**与包名无关**——放公共源只写一份、两档共用；放差异层则要与另一侧各写一份仅因包名不同的相同代码。

== 跨版本二进制契约

`base` 只编译一次（每档位一次），却要在同档位的多个 MP 版本上运行，故**只允许调用"描述符跨版本不变"的 MP 方法**。已核对的集合：

[cols="2,1,1,1,1", options="header"]
|===
| 方法 | 描述符 | 3.3 | 3.4 | 3.5.16 / 3.5.17

| `save(T)`
| `(Ljava/lang/Object;)Z`
| 一致 | 一致 | 一致

| `updateById(T)`
| `(Ljava/lang/Object;)Z`
| 一致 | 一致 | 一致

| `removeById(Serializable)`
| `(Ljava/io/Serializable;)Z`
| 一致 | 一致（另有 `removeById(T)` 重载） | 一致（另有重载）

| `getById(Serializable)`
| `(Ljava/io/Serializable;)Ljava/lang/Object;`
| 一致 | 一致 | 一致

| `page(IPage)` / `page(IPage, Wrapper)`
| `(IPage)IPage` / `(IPage,Wrapper)IPage`
| 一致 | 一致 | 一致
|===

判定规则：**返回值类型参与描述符**。返回 `Integer` 与返回 `Long` 的同名方法互不兼容（见「已知限制」第 1 条）；参数只差泛型的则兼容（擦除后一致）。

== CMpController 的接法

`CMpController<S extends ICService<T>, T>` 落在 base 的 `src/main/java`（**单份，不按档位再拆镜像**）。依据是它只依赖两样东西：

. `ICService` 自己的 default：`getEntitySimpleName()`、`page(CPageReq)`（后者内部转 `page(IPage)` / `page(IPage, Wrapper)`，描述符四版一致）；
. MP 的元素级方法：`getById(Serializable)`、`save(T)`、`updateById(T)`、`removeById(Serializable)` —— 描述符四版一致（见上表）。

于是 controller 的字节码在四个版本上都能直接解析，**版本差异一层都不外泄到 controller**。

原先迫使 base 拆档位目录的唯一导入是 `javax.validation.constraints.NotNull` / `jakarta.validation.constraints.NotNull`。处理方式：

* 参数级"必填"改用 `com.c332030.ctool4j.web.validation.annotation.CRequired`（`ctool4j-web` 内部用 `src/main/java-jdk8` / `src/main/java-latest` 两套同名注解吸收 javax→jakarta 的包名差异），base 以 `provided` 引入 `ctool4j-web`——与既有的 `@CSchema` / `@COperation` 同属"文档/校验注解由使用方运行时提供"的约定；
* `@Validated` 保留（Spring 自有注解，两档同名），仍由它触发 request body 的 Bean Validation。

约束（落在评审口径里，不是可选项）：

* controller 内不得出现 `count()` / `selectCount()` 一类返回值随版本变化（`Integer` ↔ `Long`）的调用；需要这类能力时，先在 `spi/CMybatisPlusSpi` 上加一个中性方法（两侧各实现），controller 只调中性方法。
* `removeById` 在 3.4 起多了 `removeById(T)` 重载，实参静态类型是 `Serializable` 时最具体匹配仍是 `removeById(Serializable)`；**不得**为了"消歧"改成 `removeById((Object) id)`——那会绑到跨版本不一致的那一支上。
* controller 里不得直接 import 任何 `javax.*` / `jakarta.*` 包；需要容器侧能力时用 ctool4j-web / ctool4j-spring-base 已抽象好的中立类型。

== 兜底设计

* **空安全**：空主键 → `null` / `Optional.empty()`、空集合 → 空列表，全部短路、不触发查询，实现在 `spi/CMybatisPlusSpi` 的 default 里（两侧各一份）。
* **3.3 缺 `getEntityClass()`**：base 的 `CServiceImpl` 泛型解析兜底；解析不到（子类以类型变量继承、未给出具体实体）时抛 `IllegalStateException`，与 MP 自身解析失败的行为一致。
* **档位与适配侧错配**：差异层按档位挂目录，jar 里只有一侧；`-33` / `-34` 由 `settings.gradle.kts` 的 `jdk8OnlyModuleNames` 在最新 LTS 档**不予注册**，不存在"用 spring 侧 jar 跑 3.3"的组合。
* **`ctool4j-web` 缺席**：`@CRequired` 是 Bean Validation 注解，类不在 classpath 时 Spring 反射读不到该注解，退化为"不校验"，不抛错。

== 适用范围

`ctool4j-mybatis-pom` 下的全部 service / controller 基类，以及任何继承 `CServiceImpl` 的业务实现。

== 不适用与边界

* 只覆盖 `IService` / `ServiceImpl` 的**包名迁移**与元素级/分页方法。注入器（`CSqlInjector`、`CInsertIgnoreMethod` 等）、分页插件、`IEnum` 包名等差异属**版本模块**的职责（`-33` / `-34` / `ctool4j-mybatis` 各写各的）。
* 不支持"同一 classpath 内同时存在两侧"：两侧同包同名，档位与 MP 版本必须同侧。

== 测试设计

* **编译矩阵**（模块级，唯一能覆盖四个版本的机械防线）：jdk8 档编 `-33`（3.3.2）、`-34`（3.4.3.4）及其余模块（3.5.16）；latest 档编 `ctool4j-mybatis` 与 base（3.5.17）。`-33` / `-34` 不进 latest 档。
* **多源校验**：base 的两个档位目录互为镜像（相对路径集合相同），由评审口径 + 一条 `diff` 自查保证（见 `agent/AGENTS-PROJECT.MD`）；其余 MyBatis 模块不得出现第二个源目录（出现即评审不通过）。根脚本 `assertNoDuplicateJavaSources` 只查「同一档实际纳入的多个目录里全限定名重复」——档位目录与公共源目录之间不相交、天然通过，但**不查**两个档位目录是否镜像（两者永不编进同一档，路径集合无法判定谁该有谁），其"镜像"性质是本层依赖的**人工约定**（由 `diff` 核）。
* **用例**：`CMybatisPlusConfigurationTests`（各版本模块已有的装配用例）不改判；新增 `ctool4j-mybatis-base` 的 `CServiceImplTests`，覆盖 `getEntityClass()`（具体继承 / 中间层泛型承接 / 整链无具体实参报错 / 实例缓存）与三个消歧方法的空安全短路。该用例不启 Spring、不连库，故**两档各跑一次**——jdk8 档跑的是 `java-jdk8` 侧的适配桥（3.5.16），latest 档跑的是 `java-latest` 侧（3.5.17）。
* **不覆盖**：注入器生成的 SQL 文本逐字比对属版本模块既有用例，本层不重复。

== 备选方案与取舍

[cols="2,2,2", options="header"]
|===
| 方案 | 不选的原因 | 备注

| 每个版本各写一份 `CServiceImpl`
| 四份重复、必然漂移（现状即 `-33` / `-34` / `ctool4j-mybatis` 三份）
| —

| `ICService` 不继承 MP `IService`，自建稳定子集
| 会丢掉 MP 的完整能力面，使用方拿不到 `save` / `page` / 链式查询
| 已否决

| 版本模块 `srcDir` 挂 adapter 的源目录（源码覆盖 jar）
| 等于把同一份源码编进多个模块，且版本差异会从 adapter 漏回上层
| 已否决（改为一律用 jar）

| base 保留 `CMpController` 的两份档位镜像
| 为一个 `@NotNull` 导入维护两套同包同名文件，且与"公共契约单源"冲突
| 已否决（改用上游 `@CRequired`）

| 按 MP 版本再拆 `ctool4j-mybatis-35` 等模块
| 模块数翻倍；且 3.5.16 与 3.5.17 只差包名，用 base 的两个档位目录即可
| 已否决
|===
