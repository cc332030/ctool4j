== 性能测试设计思路

=== 被测对象

工具库最核心、最高频的集合转换操作：

- `convert`：集合元素映射（`List<String>` → `List<Integer>`）。
- `toMap`：集合转 Map（`List<Item>` → `Map<Long, Item>`，元素自身为值）。
- `toMap`（key 过滤 + value 提取）：`List<Item>` → `Map<Long, String>`，按 key 过滤、单独提取 value（覆盖 `toKey` 单遍调用的优化路径）。
- `groupingBy`：集合分组（`List<Item>` → `Map<Integer, List<Item>>`）。
- `filter`：集合过滤（`List<Integer>` 过滤偶数）。
- `first`：获取集合首个元素（`List<Item>`）。
- `last`：获取集合末个元素（`List<Item>`）。
- `min`：按转换结果取最小值（`List<Item>` → `Item`，按 id 取最小）。
- `max`：按转换结果取最大值（`List<Item>` → `Item`，按 id 取最大）。

=== 对比维度（≥3 类实现，实现原理各不相同）

- `CCollUtils`（被测）：C 工具类封装 stream + Collectors，含判空/过滤/空集合兜底等语义。
- 原生 stream + Collectors：JDK 直接实现（`stream().map/filter/collect`、`Collectors.toMap/toList/groupingBy`、`stream().findFirst/reduce/min/max`）。
- hutool `CollUtil`：第三方工具类实现（`CollUtil.map`）。
- 手工循环：编译期直接赋值的基线（`for` 循环手工操作集合，列表按索引取值）。
- `toMap` 过滤 + value 提取维度同样提供 CCollUtils 与手工循环两种对比实现（验证 `toKey` 单遍调用优化）。

=== 执行方式

- 性能测试独立于单元测试，仅在明确命令执行时才运行（`mvn test -Dtest=CCollUtilsBenchmarkTests`）。
- 排除初始化干扰：先对所有用例做一轮全局预热，触发全部实现方式初始化/加载，首次结果不计入。
- 充分预热 + 足够迭代：预热 50 万次触发 JIT 至 C2 稳态，单轮计时 100 万次、取 5 轮平均，降低测量噪声。
- 结果写入 `tmp/benchmark-report-ccollutils.md` 报告，分析性能差异原因并给出方案。

== 性能分析结论

以手工循环为基线（1.00x），本次采样数据（100 元素集合，相对基线）：

- `CCollUtils.convert` 约 5.2x、`toMap` 约 8.4x，相对原生 stream 更慢。原因：CCollUtils 底层封装 stream + Collectors，并在语义上额外承担**空集合判空、null 元素过滤**、`toMap` 额外返回**不可变 Map**（包装拷贝）等健壮性代价。
- `toMap`（key 过滤 + value 提取）经单遍循环优化：`toKey` 每个元素仅执行一次（原实现经 filter/first/forEach 重复调用，命中元素重复 2 次），并避免中间集合，消除重复转换与多余遍历。
- `CCollUtils.groupingBy`、`filter` 接近原生实现（约 3~3.7x），表现良好。
- 手工循环始终最快（编译期确定性分配，零语义开销）。

`first`/`last`/`min`/`max` 为高频取元素/最值操作，CCollUtils 选取更轻量实现：

- `first`：List 走索引 `get(0)`（O(1)），非 List 走迭代器，避免构造 Stream。
- `last`：List 走索引 `get(size-1)`（O(1)），非 List 走迭代器单遍遍历，避免 Stream reduce lambda 累积开销。
- `min`/`max`：单遍循环，**每元素仅执行一次 `convert`**（原 Stream 实现在过滤与比较阶段对 `convert` 重复执行两次），降低用户函数调用开销。

方案建议：
- 对**高频热路径且数据规模大**的集合转换，若不需要 null 过滤/不可变 Map 等健壮性语义，可优先使用原生 stream 或手工循环；CCollUtils 则适合作为**默认安全选择**，其健壮性语义（判空、过滤 null、不可变）在绝大多数业务场景下收益大于微小的性能开销。
- 不需要不可变 Map 的场景，评估是否可走 `toMap` 的可变变体（如交由调用方决定容器），以降低包装开销。
- `first`/`last`/`min`/`max` 优化后与手工循环差距大幅缩小，适合作为默认取元素/最值入口。
