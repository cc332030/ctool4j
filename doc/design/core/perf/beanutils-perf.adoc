= CBeanUtils 性能实测记录

本文件记录 `CBeanUtils` 对象属性复制与深拷贝的**性能实测**：测量口径、各方案成绩、瓶颈归因、
优化日志与选型结论。用例级细节（对比了哪些方案、测量配置）见 `CBeanUtilsPerfTests` 的类/方法 javadoc；
本文件承载**跨轮次、跨方案**的内容。

原始报告（一次性产物，仅留证）随本文件同目录落盘：
`benchmark-report-cbeanutils-copy.md`、`-deepcopy.md`、`-tomap.md`。

== 运行环境与适用条件

|===

| 运行时 | JDK 8（Temurin 8u504，与 `pom.xml` 声明的 `java.version=8` 一致）
| 构建 | Maven 3.8.7，`mvn -Pperf`（`PerfTests` 独立于常规测试、须显式触发）

  -Dtest=CBeanUtilsPerfTests -Dsurefire.failIfNoSpecifiedTests=false test
----

== 测量口径

- **预热**：第一轮对全部用例预热（触发各实现的初始化与加载），不计时；随后每轮计时前再预热一次。
- **测量**：每用例 5 轮（≥3 次有效采样），简 copy / toMap 通道单轮 100 万次、深 copy 通道单轮 20 万次。
- **取数**：终值 = 各轮「单次均摊耗时」的均值；**离散度 = 极差（最慢 − 最快）**，两者同表给出。
- **判定**：组间差异小于两者离散度之和即标「无显著差异」，不据此宣称胜出。
- **计时区间**：只含被测调用循环——数据构造（`prepare`）与报告写出都在区间外；每轮计时前归集一次垃圾，各轮同状态起步。
- **结果消费**：被测调用返回值经 `identityHashCode` 累加进 blackhole，防 JIT 整体消除死代码。

== 瓶颈归因

归因以"同一 JVM 内交替测量的 A/B 对照"为准（不靠复杂度估计）。

=== 归因一：通用字段访问的机制成本（不可消除）

实测（7 轮取均值，单独测量字段访问循环）：

[cols="3,2,3", options="header"]
|===
| 访问机制 | 耗时(ns/op) | 说明

| 直接 setter（JIT 内联为字段读写） | 22.9 | 需**生成字节码**才能对任意类做到；本类明确不做字节码处理
| `MethodHandle.invokeExact` | 69.5 | 本类当前机制
| `Field.get`/`Field.set` | 106.5 | 反射，比 MethodHandle 慢约 1.5 倍
|===

判断依据：同一份 7 字段 Bean、同一 JVM、同轮次交替测量。

**结论**：`MethodHandle` 是"不使用字节码处理"前提下的**最优可用机制**——反射更慢、直接 setter 需字节码。
本类与手工 setter 的差距属**通用性代价**，不构成可优化项。

同时确认：CBeanUtils 的字段循环**仅比"裸 MethodHandle 循环"多约 11%**
（裸 7× getter+setter 循环 66.5ns vs `copy` 复用目标 74.9ns），框架自身开销已接近下限。

=== 归因二：容器创建的重复判定（已优化）

判断依据：单独测量各判定单元——4 段 `isAssignableFrom` 链 **50.3ns**、`ClassValue` 查表 2.9ns、
`sun.reflect` 构造器扫描 23.7ns。深拷贝每次建容器都要走这条链，而结果只依赖目标类。

**对策**：目标派生判定按目标类缓存（一次 `ClassValue` 查表）。

=== 归因三：身份表的默认容量（已优化）

判断依据：`new IdentityHashMap<>()` **49.2ns**（默认按 32 槽建表）vs `new IdentityHashMap<>(4)` **22.4ns**。
而一次复制的参与对象通常只有个位数：只要出现任一可变字段就会按需创建身份表，
等于每次复制多分配一个 32 槽空数组。

**对策**：显式按 4 起步。

=== 归因四：泛型实参的重复解析（已优化）

判断依据：`deepCopyTypeArgument` **8.3ns/次**（`Type` 走查 + 通配符收敛）、
`isDefinitelyImmutable` **9.1ns/次**；两者只依赖 `Type`，却按"每次复制"重算。

**对策**：按 `(声明泛型, 位置)` 缓存"类型 + 不可变标志"，热路径只查表。

== 第 2 轮：按类折叠候选的同口径 A/B（本次）

本轮评估三处"不改架构、风险低"的候选优化，逐项做同口径 A/B，**以实测是否有收益决定去留**。

=== 测量口径（本轮 A/B）

- 夹具：临时 A/B 程序（同进程内交替测量；两版各自实现的同语义内联/真实变体），逐场景 9 轮采样、
  报极差离散度；组间差异小于两者离散度之和即判「无显著差异」。
- 端到端参照：真实 `CBeanUtils.copy`（同一 JVM、每轮归集垃圾、`prepare` 在计时区间外、
  返回值经 `identityHashCode` 消费），并**交替重启 JVM**跑两版（抵消机器漂移），每版 3 轮。
- 场景按"一次 copy 命中目标类 gate 的次数"设计，使按类恒定判定的差异可被观测。

== 未选方案为什么不选

- **反射（`Field.get`/`set`）**：比 MethodHandle 慢约 1.5 倍（106.5 vs 69.5 ns/op），无理由替换。
- **Caffeine 缓存**：在"条目少、访问极热"的场景下查表与键分配高于裸 `ConcurrentHashMap`，
  实测退化 56%（153 → 239ns），不采用。
- **生成字节码（ASM/ByteBuddy）**：可接近手工 setter，但用户明确排除，且引入构建期/运行期复杂度。
- **缓存按 (值类型, 目标类型) 的决议结果**：已在既有实现中（`COPY_ACTION_BI_CLASS_VALUE` + 条目内 `ActionMemo`），无需另立。
- **按 Type 的数组槽缓存**：与对象键版无显著差异，收益在离散度内，不引入额外数据结构。
- **`newStandardContainer` 折叠为按目标类的 kind 查表**（第 2 轮候选 B）：实测明显更慢
  （隔离 +39.9ns、端到端三场景 +34~+88ns）。原因：整型 `if` 链在 JIT 下分支预测稳定、可被 C2 消除，
  而新增的一次 `ClassValue` 查表（5.9ns）是实打实的成本——"减少分支"不等于"更快"，须以实测为准。
- **`toMap` 用 `put` 返回值判冲突**（第 2 轮候选 C）：差异在离散度内、无显著收益；
  `putIfAbsent` 的"是否缺席"内部分支已被 JIT 内联，去掉返回值的 null 判断不减少实际分支。

== 迭代收敛判定

- 第 1-3 轮为**有效收益**（边际收益均超过同口径离散度）。
- 第 3' 轮为**负收益**（回滚）；第 3''、4 轮为**无显著收益**（差异 < 离散度，回滚）。
- 第 2 轮：第 5 轮为**有效收益**（-2.3%~-3.5%，随命中次数放大，与隔离测量吻合）；
  第 6 轮为**负收益**（回滚）；第 7 轮为**无显著收益**（回滚）。
- 剩余差距经归因确认落在**不可消除项**：`MethodHandle` 固有成本 + 每次复制的必要分配
  （容器、身份表）。继续优化的方向只剩字节码处理（已排除），故**判定收敛**。

== 结论与选型

- **选中方案**：维持现有的"计划预计算 + `MethodHandle` + 单一决议/执行"架构，
  叠加第一轮三项缓存/容量优化（① 容器实现判定按类缓存 ② 身份表按小容量创建 ③ 泛型实参解析缓存）
  与第二轮一项按类折叠优化（④ 深拷贝按目标类折叠 `DeepPlan`，见下）。
- **代价**：新增一个按声明泛型缓存的有上限 `ConcurrentHashMap`（条目数与类元数据同生命周期，
  上限守卫防极端增长）；其余两项为纯参数调整，无新状态。
- **收益**：第一轮深拷贝在集合/Map/数组场景实测提升 10%-44%；第二轮 `DeepPlan` 折叠按"一次复制
  命中的目标类次数"线性生效（命中 13 次 -2.3%、41 次 -3.5%，隔离测量每次命中省 4.4-4.9ns）；
  简单 copy 与 toMap 通道以机制为瓶颈、未变。
- **第二轮采选经过**：候选 A（`DeepPlan` 折叠）采纳；候选 B（容器创建 kind 查表）、
  C（toMap 冲突检测）经同口径实测无显著收益或负收益，**未采纳**（理由见「未选方案为什么不选」）。
- **未选方案**：见上「未选方案为什么不选」。
- **行为不变**：全部优化在既有功能用例全绿下取得（`ctool4j-core` **780 用例 0 失败**、
  全仓 **1998 用例 0 失败**），对外可观测行为、边界与默认值、错误语义均未改变。
  第二轮折叠时**刻意不把「构造体抛异常」并入按类计划**——该项是运行期可变状态
  （登记时刻可能晚于计划创建），按类缓存会把"登记前"的取值固化、此后永远看不到登记结果，
  实测中该做法直接触发既有用例 `uninstantiableByThrowingCtor_registeredOnceAndSkipped` 失败，
  已改回运行期查（设计取舍记录见 `CBeanUtils.DeepPlan` javadoc）。
