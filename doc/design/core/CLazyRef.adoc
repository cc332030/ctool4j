= CLazyRef 设计文档

Version: 1.7
LastModified: 2026-09-10
模块：ctool4j-core
类：com.c332030.ctool4j.core.util.CLazyRef
状态：已落地
适用范围：懒加载值持有器（封装双重检查锁，仅在首次使用时求值）

== 1. 功能说明

`CLazyRef<T>` 为懒加载值持有器，实现 `java.util.function.Supplier<T>`：

- `of(Supplier<T>)`：静态工厂，创建持有器（不立即求值）。
- `get()`：首次调用时执行 supplier 求值并缓存，后续直接返回缓存值。

设计目标：把"判空 + 加锁 + 缓存"的双重检查锁（DCL）样板封装到一个可复用类中，使用方只需
`CLazyRef.of(() -> xxx)` 声明字段即可获得线程安全的懒加载，无需重复编写 DCL 代码。

命名：`CLazyRef` 遵循本项目"类统一 `C` 前缀"规范；`Ref` 后缀表示"对一个值的延迟引用持有"，
与 core 模块既有 `CRefClassValue`/`CRefBiClassValue` 的 `Ref` 用法一致。该名与 `java.lang.Lazy`
（JDK 实际无此类）无继承/扩展关系，仅借语义相近的 `Lazy` 命名。

== 2. 设计要点

=== 2.1 双重检查锁（DCL）封装

- 字段 `volatile boolean initialized` 作为求值标志，`T value` 保存结果。
- `get()`：先读 `initialized`（无锁快速路径），未求值才进入 `synchronized(this)` 二次判空并求值。
- `value` 无需 volatile：写 `value` 在 `synchronized` 内，其后写 `initialized=true`；
  读线程通过 volatile 读 `initialized==true` 建立 happens-before，能看见之前的 `value` 写。

=== 2.2 null 结果缓存

- 用 `initialized` 标志（而非 `value != null`）判断是否已求值：supplier 返回 `null` 时同样只求值一次，
  避免"结果为 null 导致每次都重新求值"的常见缺陷。

=== 2.3 类加载延迟（class not found 防御）

- 关键用途：类字段声明为 `CLazyRef`，可把"可选依赖类的加载/初始化"推迟到真正 `get()` 时，
  避免类初始化阶段因 supplier 引用的类缺失而抛 `NoClassDefFoundError`。
- 各种 supplier 写法在**依赖存在**时均正常可用、不抛异常：**lambda**（`() -> X.create()`）、
  **静态方法引用**（`X::create`）、**实例方法引用**（`instance::create`），可直接声明为具体类型
  `CLazyRef<X>`；`CLazyRef` 亦可直接用于**静态字段初始化**（用例 1.7~1.12）。
- **依赖可能缺失**时（调用方可能未引入，期望"不调用则不加载"），能否延迟到 `get()` 取决于写法：
  - **方法引用**（`X::new` / `X::create`）或 **lambda 返回具体类型 `X`**：构造 supplier 时即需解析
    `X` 的类型，目标类会在**类初始化**阶段被加载，缺失时即抛错，无法延迟到 `get()`——方法引用缺失时
    报 `invokedynamic` 引导失败的 `BootstrapMethodError`（cause 为 `NoClassDefFoundError`，用例 1.14
    记录该限制）；lambda 未擦除时同理（该 lambda 写法未单独建用例，见测试文档"未覆盖"）。
  - **lambda + 返回类型擦除为 `Object`**（`() -> (Object) new X()`，即 `CLazyLambdaDepHolder` 的写法）：
    可完全延迟到首次 `get()`，缺失时在 `get()` 才抛错（用例 1.13）。
- 上述两种写法分别由 `CLazyLambdaDepHolder`（擦除写法）与 `CLazyMethodRefDepHolder`（具体类型写法）
  承载，各在"有依赖 / 无依赖"两种环境验证（用例 1.11~1.14）：有依赖时两种写法均不抛异常；
  无依赖时擦除写法初始化通过、取值才抛错，具体类型写法初始化即抛错。
- **实践建议**：`CIdUtils.UUID_V7_GENERATOR` 属"依赖可能缺失"场景，必须用 `CLazyRef<Object>` +
  **擦除返回类型的 lambda**（`() -> (Object) Generators.timeBasedEpochGenerator()`），取值时强转。
  java-uuid-generator 为 Maven `optional`，依赖它的模块（如 `ctool4j-mybatis-base`）**不一定引入**，
  而 `CIdUtils` 会被 `CBizIdUtils` 等间接触发类加载——若不擦除，这些模块将在类初始化阶段抛
  `NoClassDefFoundError`。此**曾为真实缺陷**（提交 `5cbafe06` 将原方法体延迟写法改为未擦除的字段
  lambda，导致 `ctool4j-mybatis-base` 的 `CBizIdUtilsTests` 全量测试失败），已按本节规范修复。

=== 2.4 线程安全

- 求值路径由 `synchronized(this)` 保护，并发首次 `get()` 也只会执行一次 supplier（其余线程阻塞后读缓存）。

== 3. 兜底设计

| 场景 | 兜底行为 |
|------|---------|
| supplier 为 null | `of` 抛 `IllegalArgumentException`（Lombok `@NonNull` 生成，非 `NullPointerException`） |
| supplier 返回 null | 缓存 null，只求值一次，后续 get 返回 null |
| 首次 get 抛异常 | 异常向上抛出，`initialized` 保持 false，下次 get 重新尝试求值 |
| 并发首次 get | 只执行一次 supplier，其余线程等待后读同一结果 |

== 4. 适用范围

=== 4.1 适用场景

- 昂贵对象的懒初始化（生成器、连接、客户端等），且线程安全共享。
- 可选依赖的延迟加载（避免类初始化阶段触发 `NoClassDefFoundError`）。
- 替代手写双重检查锁样板。

=== 4.2 不适用/边界场景

- 不需要线程安全、或要求"每次 get 都重新求值"时不应使用。
- 不支持"求值失败后自动多次重试缓存"，异常时下次 get 会重新求值。

== 5. 已知限制与取舍

- 求值失败不缓存（下次 get 重新求值），符合"失败可重试"预期；如需缓存失败需外部处理。
- 单值持有，不支持按 key 分别懒加载（按 key 场景用 `cache.impl.CClassValue` 或缓存实现）。
- 因封装了 `synchronized`，首次求值存在一次锁开销；已通过无锁快速路径（volatile 读）规避稳态开销。

测试内容见 `doc/design/core/CLazyRefTests.adoc`。
